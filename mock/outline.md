# Helper Page
## Basics
Helper selects from the list of available disciplines and the list of classes with each around 25-30 participants. A helper most of the time only serves one discipline the whole day. The classes rotate between the disciplines. 
There are currently 4 disciplines: (800m run, 50m sprint, 3-jump and distance throw). There could be more disciplines in the future. 
## Offline usage 
The system should be designed to work offline, allowing helpers to record data and manage the competition without an internet connection. This is crucial for ensuring that the system can be used in various locations and conditions where internet access may not be reliable. The system should store data locally on the device being used by the helper and synchronize with a central database when an internet connection is available.
### Synchronisation
When an internet connection is available, the system should automatically synchronize the locally stored data with a central database. This synchronization process should ensure that all recorded performances, scores, and rankings are updated in real-time across all devices and platforms. The system should also handle any conflicts that may arise during synchronization, such as duplicate entries or discrepancies in data, by implementing a robust conflict resolution mechanism. Additionally, the system should provide feedback to the helper regarding the status of the synchronization process, including any errors or issues that may occur. Also a overview of open data points that need to be synchronized should be provided to the helper.
### Reload of page
The system should allow for the reloading of the page without losing any recorded data. This means that if a helper accidentally refreshes the page or navigates away and then returns, all previously entered data should still be intact and available for use. The system should implement a mechanism to save the state of the page and the recorded data locally, ensuring that it can be restored upon reload. This could involve using local storage or IndexedDB to temporarily store the data until it is synchronized with the central database. The system should also provide a confirmation prompt before allowing the page to be reloaded, warning the helper about potential data loss and giving them the option to cancel the reload if they wish to preserve their data.
Also all required assets should be cached to ensure that the system can function smoothly even without an internet connection. This includes caching the necessary scripts, stylesheets, and any other resources needed for the system to operate effectively. The caching mechanism should be designed to update the cached assets when new versions are available, ensuring that helpers always have access to the latest features and improvements.
All needed data for the disciplines, classes and participants should be preloaded to ensure that the system can function smoothly without an internet connection. This includes preloading the list of available disciplines, the list of classes with their respective participants, and any relevant information about the participants (such as their names, ages, and class levels). The preloading process should be designed to efficiently load this data into the system's local storage or memory, allowing helpers to access it quickly when needed. Additionally, the system should provide a mechanism for updating this preloaded data when changes occur, such as adding new disciplines or updating participant information, ensuring that helpers always have access to the most up-to-date information.
## User interface
The user interface be designed to be intuitive and user-friendly, allowing helpers to easily navigate through the system and perform their tasks efficiently. The interface should provide clear instructions and prompts for recording performances. It should also include features such as dropdown menus, search functionality, and filters to help helpers quickly find the relevant information they need. 
The design should prioritize ease of use and minimize the learning curve for helpers, ensuring that they can quickly become proficient in using the system to manage the competition effectively.
Also a fast input of data is crucial, so the interface should be optimized for quick data entry, allowing helpers to record performances and manage the competition efficiently. This could involve implementing features such as keyboard shortcuts, auto-complete functionality, and streamlined forms to facilitate rapid data input. The system should also provide real-time feedback and validation to ensure that the entered data is accurate and complete, reducing the likelihood of errors and improving the overall efficiency of the data recording process.
A good overview of all participants and their recorded performances should be provided to the helper, allowing them to easily track the progress of the competition and identify any missing or incomplete data. This could involve using tables to display the recorded performances for each participant in each discipline. The system should also allow for sorting and filtering of this data, enabling helpers to quickly find specific participants or performances as needed. The participants can run all at the same time, so the system should be designed to be able to find and update the data of each participant quickly and efficiently, even when participants arrive at diffrent times and the data is being entered in a non-sequential manner. Also the participants can arrive at very close times, so the system should be able to handle multiple entries in a short period of time without any performance issues or data loss and a fast entry.
### Indication of states
Errors or issues with the data entry should be clearly indicated to the helper, allowing them to quickly identify and resolve any problems. This could involve using visual cues such as color coding, icons to highlight errors or missing information. The system should also provide clear instructions on how to correct any issues, guiding the helper through the necessary steps to ensure that the data is accurate and complete. Additionally, the system should allow for easy editing and updating of recorded data, enabling helpers to make corrections as needed without having to navigate through complex menus or processes.
A state of the synchronization or saving process should also be indicated to the helper, providing feedback on the status of the data synchronization or saving. This could involve using visual indicators such as progress bars, status messages, or icons to show whether the data is being saved locally, synchronized with the central database, or if there are any issues with the synchronization process. The system should also provide clear instructions on how to resolve any synchronization issues, guiding the helper through the necessary steps to ensure that their data is properly saved and synchronized.
Given a new input field, the system should also indicate whether the input is saved to local storage and whether it is synchronized with the central database. This could involve using visual cues such as icons next to the input field to show whether the data has been saved locally and whether it has been successfully synchronized. The system should also provide feedback on any errors or issues that may occur during the saving or synchronization process, allowing helpers to quickly identify and resolve any problems with their data entry.
### Responsive 
Additionally, the interface should be responsive and accessible on various devices, including desktops, tablets, and smartphones, to accommodate different user preferences and needs.

# Central interface
The central interface is a platform that allows for the management and analysis of the recorded data from the various disciplines and classes. It provides a comprehensive overview of the competition, including overall rankings, individual and class rankings in each class level, rankings in each discipline, and the ranking of the best class or individual. The central interface should be designed to be user-friendly and intuitive, allowing administrators and organizers to easily navigate through the data and generate reports as needed. It should also provide tools for filtering and sorting the data, enabling users to quickly find specific information or analyze trends across different disciplines and classes. Additionally, the central interface should allow for the export of data in various formats, such as CSV or PDF, to facilitate further analysis or sharing of results with participants and stakeholders.
The central interface should also include features for managing the competition, such as adding or removing disciplines, classes, and participants, as well as updating the scoring tables and conversion scales. The interface should also allow for real-time updates and synchronization with the data recorded by the helpers, ensuring that all information is up-to-date and accurate across all platforms. Additionally, the central interface should provide tools for analyzing the performance of participants and classes, such as generating graphs and charts to visualize trends and comparisons across different disciplines and class levels.

# Disciplines
## 800m run
The 800m run is a middle-distance running event. It consists of two laps around a standard 400m track. For each participant, the time taken to complete the 800m run is recorded in seconds.
## 50m sprint
The 50m sprint is a short-distance running event. It is a straight sprint on a 50m track. The time taken to complete the 50m sprint is recorded for each participant in seconds.
## 3-jump
The 3-jump, also known as the triple jump, is a track and field event where participants perform a hop, a step, and a jump in sequence. The distance covered from the takeoff point to the landing point is measured for each participant in meters. Currently two tries are allowed for each participant, but this may be changed in the future. Each participant's jump is recorded, but only the best jump is used for scoring purposes.
## Distance throw
The distance throw is a field event where participants throw an 200g ball as far as possible. The distance from the throwing point to the landing point of the object is measured for each participant in meters. Currently two tries are allowed for each participant, but this may be changed in the future. Each participant's throw is recorded, but only the best throw is used for scoring purposes.
# Scoring
A predifined scoring table for each discipline is used to convert the raw performance (time or distance) into points. The scoring table assigns points based on the performance of the participant, with better performances earning more points. The total points accumulated across all disciplines determine the overall ranking of the participants in the competition while each is weighted evenly.
A diffrent scoring table is used for each discipline, gender and class level. It is currently given as a table with the raw performance and the corresponding points. They maybe converted into a formula in the future, because a score above the maximum performance in the table is currently not possible to calculate.
## Marks
The total points are also converted into marks, which are used to determine the final grade of the participant. The conversion from points to marks is based on a predefined scale, where a certain range of points corresponds to a specific mark. The marks are typically represented as numbers (1-6 or 15-0) depending on the class level. A change to the conversion scale may be made in the future, but currently it is given as a table with the points and the corresponding marks.
# False starts or invalid attempts
In the case of a false start in the running events (800m run and 50m sprint) or in the case of an invalid attempt in the field events (3-jump and distance throw) or any future disciplines, the participant can repeat the attempt as many times as needed until a valid attempt is made. Only valid attempts are recorded and used for scoring purposes. The system should allow for multiple attempts and ensure that only the best valid attempt is considered for scoring. Any invalid attempts should not be recorded
# Data recording and management
The system should have a user-friendly interface for recording the performance of each participant in each discipline and the analysis and management. The data should be stored securely and organized in a way that allows for easy retrieval and analysis. The system should also allow for the generation of reports and summaries based on the recorded data, such as overall rankings, individual and class rankings in each class level, rankings in each discipline, ranking of the best class or individual. All data should be gathered on a central system.
